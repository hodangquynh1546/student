# Security and student privacy

Authentication uses short lived signed JWT access tokens and opaque rotating refresh credentials stored as hashes. Browser refresh uses an HttpOnly, Secure, SameSite cookie. Passwords use BCrypt. Activation and reset tokens are single use, hashed at rest and expire. A second use of a rotated refresh credential revokes its family. Production must reject a missing/default JWT secret and weak admin bootstrap credentials.

Authorization has two layers: role checks at the API boundary and resource checks inside each service. The `studentId` in a route or body is never proof of access. Student reads/writes require the JWT subject and active assignment or own attempt. Parent reads require an unrevoked verified `parent_student_links` row and publication check. A student must never receive another student's answer, grade, identity or private ranking data. Use consistent `404` for hidden resources where revealing existence would itself leak data.

Exam answers and rubrics live on teacher/grading paths only. Build student DTOs by explicit allowlist. Do not serialize a JPA entity or reuse a teacher DTO. Scrub correct flags from question `content` as well as `answer_key`. Answer release after submit must verify both exam settings and the time/status policy. Logs and audit records may identify actor/subject IDs but must not contain raw passwords, refresh tokens, activation tokens, student essay images or full AI prompts.

Use CORS allowlist from environment. The refresh cookie authenticates `/auth/refresh` and `/auth/logout`; those endpoints require a configured browser Origin, or a same-origin Fetch Metadata header when Origin is absent. The cookie also uses strict SameSite. Spring CSRF remains disabled for bearer-token API routes; verify this cookie boundary in a real browser before production. Limit login, reset, activation, invitation and AI endpoints by IP/account and return generic recovery messages. Enforce upload size, MIME sniffing, file extension allowlist, randomized storage names and per-file download authorization. Sanitize any allowed HTML and render math with a safe library configuration.

Audit teacher actions: student creation/lock, parent invitation/accept/revoke, enrollment changes, exam publication, result publication and every grade change. Use a correlation ID for tracing requests without recording secrets. Integration tests must cover role boundaries and student A versus student B, parent with/without accepted link, expired/revoked invitation, concurrent submit, and answer-key embargo.

Current implementation has an in-process IP rate limit on login, password recovery, activation and refresh, plus per-user in-process limits on the learning and question-draft AI routes. These are not shared across replicas and need a shared store or edge controls for horizontal scaling. Private essay attachments use an authorized download route and are bound to an attempt; result publication and active parent link are checked before parent access. The import endpoint is teacher-only, limits file and row counts, rejects Excel formula cells and validates each account through the normal creation service. Rankings return only a learner's own metrics to student and parent callers. Reports check student ownership or active verified family link before listing/exporting snapshots.

Production assurance remains incomplete. The refresh/logout browser Origin guard has unit tests but still needs real browser verification. HTML sanitization, broader upload and concurrency tests, and full browser end-to-end authorization checks remain release gates. Assignment and result-publication email uses a durable outbox, but real SMTP delivery remains unverified. AI tutoring does not load answer keys and requires a closed/ended exam before using a published attempt as context; generated question drafts must be reviewed and validated by the normal question creation path before use.
